### 基本方針

- 機能追加・振る舞いの変更・バグ修正は、原則として TDD（テスト駆動開発）で進める。
- 小さな振る舞いごとに、必ず **RED → GREEN → REFACTOR** の順で進める。実装を先に完成させてからテストを追加しない。
- テストは利用者や呼び出し側から見た振る舞いを検証する。内部実装をそのまま写したテストや、モックの呼び出し確認だけで正しさを判断するテストを避ける。

### 検証コマンドと環境

- 以下のコマンドを TDD の各段階の検証に使い、変更後の必須チェックとしても実行する。
  - JavaScript／TypeScript（JSX／TSX を含む）を変更したら、`bun run test` を実行する。
  - Rust のコードや依存関係を変更したら、対象の Cargo プロジェクトで `cargo check` と `cargo test` を実行する。Tauri の Rust プロジェクトが `src-tauri` にある場合は、`--manifest-path src-tauri/Cargo.toml` を指定する。
- テスト環境が未整備なら、機能実装より先に必要なテスト設定を用意する。
- 必要なテストスクリプトや Cargo プロジェクトの不足、環境制約などで検証できない場合は、理由、未検証の範囲、再実行方法を報告する。実行できていない RED／GREEN を確認済みとしない。

### RED：失敗するテストを書く

1. 期待する振る舞いと受け入れ条件を明確にし、次に実装する最小の振る舞いを選ぶ。
2. 実装を変更する前に、その振る舞いを検証するテストを書く。バグ修正では、バグを再現するテストを書く。
3. テストを実行し、機能の未実装や対象のバグによって、意図した理由で失敗することを確認する。
4. 構文ミス、依存不足、テスト設定の不備、OS の環境不足などによる失敗は RED の確認に数えない。先に検証環境を整える。

### GREEN：最小限の実装で通す

1. RED で確認したテストを通すために必要な実装だけを加える。
2. 対象のテストと関連する既存テストを実行し、成功を確認する。
3. テストを通すために期待値を都合よく変えたり、テストを削除・スキップしたりしない。仕様やテストに誤りがあった場合は、理由を説明して修正する。

### REFACTOR：振る舞いを保って整理する

1. テストが通っている状態で、重複、命名、責務の分離などを改善する。
2. 整理の後に対象のテストと関連する既存テストを再実行し、振る舞いが変わっていないことを確認する。
3. 必要な改善がなければ、その旨を記録して次の RED に進む。この段階で新しい振る舞いを追加しない。

### Tauri でのテスト方針

- Rust の業務ロジックは Tauri コマンドや OS 操作から分離し、可能な限り通常の関数として `cargo test` で検証する。
- React／TypeScript のロジックや UI の振る舞いは、Bun で実行するテストで検証する。必要に応じて DOM を扱えるテスト環境を使う。
- IPC、ファイル操作、ダイアログなどの境界では、必要に応じてモックや依存の差し替えを使う。ただし、モックの成功だけでは実際の Tauri 連携が動くと判断しない。
- コマンド登録、capabilities、WebView、OS 固有機能などは、利用可能な環境で統合テスト・E2E テストや実機確認を行う。
- 自動テストが難しい部分は、理由、テストできる範囲、代替の検証手順を明示する。テスト可能なロジックには引き続き TDD を適用する。

### 適用範囲と完了報告

- 文書だけの変更や振る舞いを変えない整形には、新しいテストを要求しない。既存コードのリファクタリングでは、変更前後に関連テストを実行し、カバレッジが不足している場合は先に現状の振る舞いを検証するテストを追加する。
- 完了報告には、RED で確認した失敗の理由、GREEN の実行結果、REFACTOR の内容と再検証結果を簡潔に含める。
- テスト、型チェック、ビルド、手動確認の結果は区別し、実行していない検証を成功したと報告しない。

### 人間への確認依頼

- レビューを依頼するときは、確認する画面・資料、操作手順、期待する結果や判断してほしい点を具体的に提示する。「画面をご確認ください」だけで済ませない。
- 依頼する確認事項は今回の変更に関係する項目に絞り、短い箇条書きで示す。見た目の判断と、操作して確かめる動作の確認を区別する。
- 自動検証済みの事項と、人間に確認してほしい未検証の事項を区別する。実機確認を依頼する場合は対象環境と手順を明記する。

### 未検証箇所の扱い

- 環境制約などで必須の検証を実行できない場合は、未検証の項目、理由、影響、代替の検証結果、再実行方法を完了報告と PR 本文に記載する。
- 未検証のまま完了条件を満たしたとは扱わない。PR は未検証であることを明記して作成してよいが、人間が未検証の範囲と影響を確認し、マージ可否を判断するまでマージを保留する。
- 環境による実行不能と、実行したテストの失敗を区別する。実装に起因するテスト失敗は修正して再検証する。
