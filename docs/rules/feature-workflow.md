### 機能開発フロー

機能開発は、以下の順序で進める。開発・テストの段階では、[TDD の手順](testing.md)を適用する。

1. **計画書作成**：要求を整理し、実装方針、完了条件、影響箇所、作業単位を、[計画ファイルの形式](plan-format.md)に従って `docs/plans/` 配下の Markdown ファイルに保存する。
2. **計画書の人間レビュー**：作成した計画書へのリンクと確認してほしい点を提示し、ユーザーにレビューを依頼する。
3. **修正（あれば）**：レビューの指摘を計画書に反映し、変更箇所を示して再レビューを受ける。
4. **開発・テスト**：計画書のレビューでユーザーの承認を得たら、その計画に沿って実装し、必要な検証を行う。
5. **実装の人間レビュー**：変更内容と検証結果、確認対象・操作手順・確認ポイントを提示し、ユーザーのレビューを受ける。指摘があれば修正・再検証し、再レビューを受ける。
6. **プルリクエスト作成**：レビューでの指摘が解消された後、プルリクエストを作成する。

- 計画についての確認は、作成した計画書への人間レビューに一本化する。そのレビューでの承認を開発開始の承認として扱い、別途の開発開始確認は求めない。計画書の作成・修正はレビュー前に進めてよいが、実装はレビューで承認を得てから開始する。
- 要求された機能開発で変更するファイルが **10ファイルを超える見込み**の場合は、小さい開発単位に分割してユーザーに提示する。各単位は原則として変更対象が10ファイル以下になるようにし、目的、範囲、想定する変更ファイル、依存関係、実施順序を示す。
- 分割した各開発単位について、このフローを適用する。開発中に10ファイルを超えると判明した場合も、計画を見直して分割案を提示する。

### 適用範囲

- 機能追加・振る舞いの変更には、上記のフローを適用する。
- 文書のみの変更は、計画書の作成とその人間レビューを省略し、依頼内容に沿って編集・確認して結果を提示する。コミット・PR・マージの運用は [Git ワークフロー](git-workflow.md) に従う。
- 小さなバグ修正でも、コードの振る舞いを変える場合は原則として上記のフローを適用する。ユーザーが明示的に簡略化を指示した場合も、バグの再現テストと必要な検証は省略しない。

### 開発中の計画変更

- 完了条件、機能の範囲、共通デザイン方針を変更する場合は、変更理由と影響をユーザーに提示し、計画ファイルを更新する。変更後の計画について明示的な再承認を得るまで、変更に依存する実装は進めない。
- 完了条件や機能の範囲を変えない実装上の調整は、判断理由を計画ファイルに記録して進めてよい。本番用依存関係の追加など、別途確認が必要な事項は各ルールに従う。
- EPUB の対応範囲、性能目標、保存データに関わる計画では、[製品仕様の検討事項](../PRODUCT_REQUIREMENTS.md) を確認し、必要な未決定事項をユーザーと決めてから完了条件に反映する。
