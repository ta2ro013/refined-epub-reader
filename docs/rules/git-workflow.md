## ブランチ・コミット・プルリクエストのルール

### ブランチ戦略（GitHub Flow）

- `main` を統合先とし、常に動作する状態を保つ。
- エージェントは、作業開始時に最新の `main` から作業ブランチを作成する。変更をコミットし、プルリクエストを通じて `main` に統合する。
- 長期運用する `develop` やリリース用ブランチは設けず、作業ブランチは小さい開発単位ごとに作成する。
- レビューと必要な検証を経てマージし、マージ後は作業ブランチを削除する。
- PR のマージは人間が行い、Squash merge を基本とする。エージェントは明示的な指示がない限りマージしない。
- 必須の検証に未実行のものがある場合は、[未検証箇所の扱い](testing.md) に従い、人間が判断するまでマージを保留する。
- 機能開発の計画・承認・レビューの順序は、[機能開発フロー](feature-workflow.md) に従う。

### ブランチ名

`<プレフィックス>/<内容を表す短い名前>` とする。名前には英小文字とハイフンを使う（例：`feature/book-search`）。

| プレフィックス | 用途 |
| --- | --- |
| `feature/` | 機能追加 |
| `fix/` | バグ修正 |
| `hotfix/` | 緊急のバグ修正 |
| `refactor/` | 振る舞いを変えないコードの整理 |
| `docs/` | 文書の追加・更新 |
| `test/` | テストの追加・改善 |
| `chore/` | 依存関係、設定、開発環境などの保守 |

### コミット

- 各コミットは、変更内容を一言で説明できる単位にまとめる。無関係な変更を同じコミットに含めない。
- コミットメッセージは、その単位で何を変更したかを短く具体的に記述する（例：`書籍検索にタイトルの部分一致を追加`）。
- 実装とその振る舞いを検証するテストなど、同じ目的の変更は一つのコミットにまとめてよい。

### プルリクエスト

- 本文には、変更の目的・内容、検証結果を記載する。
- **変更したファイル名（リポジトリ相対パス）と、そのファイルへの参照リンクを必ず記載する。** レビューするコミットの GitHub 上のファイルにリンクし、必要に応じて対象行も示す。
- 変更ファイルは、例えば「ファイル名／参照／変更内容」の表でまとめる。
- 計画ファイルや関連 Issue がある場合は、それらへの参照リンクも記載する。
- 実行していない検証や、未検証の範囲がある場合は明記する。

### 人間による作業の扱い

- 人間が作業する場合は、`main` に直接コミットすることもある。これは許容する例外であり、ルール違反として指摘したり、作業を止めたり、取り消しを求めたりしない。
- エージェントは人間のコミットを尊重し、その内容を踏まえて作業を進める。人間による直接コミットを、エージェント自身が `main` に直接コミットする許可とは扱わない。
